# 익숙해진 뒤 WSL로 옮기기

처음에는 Windows에서 설치·로그인·작업을 모두 끝낼 수 있습니다. Linux 도구가 필요해지면 지금 쓰는 에이전트에게 이 문서를 읽고 현재 작업공간을 WSL로 옮기는 계획을 세워 달라고 요청합니다. 처음부터 다시 시작할 필요는 없습니다.

## 이관 전에 읽을 입력

현재 setup-status, Windows 작업공간의 진행 중인 작업·문턱 데이터·기존 지침, 운영 중인 앱·데몬과 경로 의존성을 확인합니다. [Microsoft WSL 설치](https://learn.microsoft.com/windows/wsl/install), [Codex WSL](https://developers.openai.com/codex/windows), [Claude WSL 설치](https://code.claude.com/docs/en/setup#install-in-wsl)의 최신 안내를 읽습니다.

## 진행 순서

1. Linux가 필요한 작업과 옮길 범위를 정합니다. 자료만 공유할지, 프로젝트를 Linux 파일 시스템으로 옮길지, Paseo 데몬까지 옮길지 구분합니다.
2. WSL 설치·재부팅처럼 사용자가 직접 할 일을 안내합니다. Windows의 기존 환경은 언제든 돌아갈 수 있는 복구 경로로 남깁니다.
3. WSL 안에 Linux용 에이전트를 설치하고 그 환경에서 직접 로그인합니다. Windows의 `.exe`·설정 폴더·인증 토큰을 그대로 복사하지 않습니다.
4. 실제 경로로 자료와 프로젝트를 연결합니다. Windows의 `C:\…`, WSL의 `/mnt/c/…`, Linux 홈을 구분하고, 같은 파일을 양쪽에서 동시에 수정하지 않도록 운영 방법을 정합니다.
5. 문턱 설치기는 플랫폼별 지원 범위를 읽고 고릅니다. Windows PowerShell 설치기를 Linux 설치기처럼 실행하지 않습니다. 기존 Bash 설치기가 이번 Windows판과 기능이 같다고 가정하지 말고, 에이전트에 필요한 로컬 scaffold와 진입 지침이 있는지 확인합니다.
6. 새 환경에서 일반 폴더 작업·문맥 로딩·쓰기·업데이트 확인·기존 기록 재조회를 다시 검사합니다. 손맛·대화 로그의 절대경로 연결도 확인합니다.
7. Paseo를 Windows에 둘지 WSL 데몬에 붙일지 정하고, 실제 provider 진단·로컬 응답·원격 응답을 다시 확인합니다. 두 데몬을 같은 포트나 서로 다른 데이터로 무심코 함께 띄우지 않습니다.

## 출력

옮긴 자료와 남겨 둔 자료, 새 경로·인증 환경·Paseo 호스트, 실제로 검증한 항목과 미확인 항목, Windows로 돌아가는 방법을 남깁니다. 이 가이드는 WSL 전체 자동 이관을 보장하지 않으며, 기존 자료 삭제는 검증을 마친 뒤 따로 판단합니다.
